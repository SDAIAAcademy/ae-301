Generative language models

A generative model is yesterday's decoder in a loop

Contextthe tokens so far
→
Decoderone score per vocabulary entry
→
Samplingscores become one chosen token
→
Appendand go round again
  • The model never writes a sentence. It scores the next token, thousands of times.
  • Everything it "knows" at a step is in the context: your instructions, the message, and what it has written so far.
  • It stops at an end token or at your max_tokens.

Link to Lab 1.3: the decoder there continued "the water" with several likely openings. A hosted model does the same at a scale of billions of parameters. Two consequences for today: output costs time per token (latency grows with length), and the choice of token is a setting you control.

Base and instruction-tuned

A chat is one long text with markers the model was trained to follow

systemYou write short replies for the contact centre of Sawaqi. Use only the facts given.
userCustomer message: … FACTS: {"ticket": "SW-48211", "crew_eta_hours": 4}
assistantthe model continues from here
  • A base model continues any text. An instruction-tuned model was trained further on conversations in one fixed format.
  • The provider's chat template turns your list of messages into that format. Use the API's roles; do not write the markers yourself.
  • The system message is not a law. It is text the model was trained to weigh heavily.

The trace shows the reply task of Lab 2.1. The last bullet prepares Day 2's theme: a prompt asks, code checks. Whatever must hold (a format, a fact, a refusal) is verified after generation, by code.

Nucleus sampling

Top-p removes the long tail before the draw

probs = (logits / temperature).softmax(-1)
order = probs.argsort(descending=True)
before = probs[order].cumsum(0) - probs[order]
# the smallest set that reaches top_p
keep = order[before < top_p]
out = torch.zeros_like(probs)
out[keep] = probs[keep]
out = out / out.sum()
  • Thousands of unlikely tokens together hold real probability. One of them, drawn, is the odd word in a reply.
  • At temperature 1.0, top_p=0.9 leaves 73 tokens of 2,000; top_p=0.5 leaves 3.
  • Use one knob at a time, and write down both.

The 73 and 3 are from the same run: the number of tokens left in the nucleus at each setting. This is the lab's first exercise. Common settings: temperature 0 for decisions and extraction; around 0.7 with top-p 0.9 for drafting.

Prompting

A prompt is a specification: say what, from what, and in which shape

You extract fields from one customer message of a water utility. The message may be in Modern Standard Arabic, Gulf dialect, Arabic in Latin script or English. Personal values are masked as [ACCOUNT_n], [PHONE_n], [NAME_n]. Return JSON only, with exactly these keys: account_number, district (one of eight, or null), complaint_type (one of sixteen). Never invent a value.
TaskInput, and what is unusual about itOutput contractThe rule that code will check

Read the prompt as a contract with four clauses. Zero-shot: no examples. Few-shot: a handful of input and output pairs, which helps most for the rare variety; the lab's stretch adds two per variety and counts what the longer prompt costs. Every clause that matters is also enforced after the call: the last one by a validator.

Structured outputs

The schema is the contract; validators check values, not only shapes

class Extraction(BaseModel, extra="forbid"):
    account_number: Optional[str]
    district: Optional[District]        # one of eight
    complaint_type: ComplaintType       # one of sixteen

    @field_validator("account_number")
    @classmethod
    def known_account(cls, value, info):
        mapping = info.context["mapping"]
        if value is not None and value not in mapping:
            raise ValueError("must be an [ACCOUNT_n] "
                             "placeholder from the message")
        return value
  • Types reject a wrong shape: a missing key, a district outside the list.
  • The validator rejects a wrong value: an account number the model never saw, a phone placeholder in the account field.
  • The error message is written for the model: it is sent back in the repair call.

The code is shortened: the lab's version also checks that the placeholder starts with [ACCOUNT_. This is the nice consequence of masking: because the model only saw placeholders, any real-looking account number in its answer is invented by construction, and the validator can prove it. Pydantic is the validation library; the same model class later defines the API's response in Lab 3.4.

The log is evidence

Message id, attempt, error. It shows what the validators stopped, and which errors repair does not fix.

Never guess

A message that fails twice gets no fields. A wrong account number is worse than none.

One repair, not five: each retry costs a call and a model that failed twice in the same way rarely succeeds the third time. The failure log is the second part of LO3's evidence. In the lab, read it by kind: text around the JSON, a wrong key, a value the validator refused.

Valid JSON every time is a format guarantee, not a correctness guarantee

  • Both end parse errors. Neither knows which district the customer lives in.
  • So measure values against gold fields: precision and recall for each field.

Retrieval-augmented generation

Facts that change live in documents, not in weights

CustomerHow much does a meter test cost and when is it refunded?
Model aloneA plausible price, from nowhere.
Model with rule R-07The answer the rule gives, with [R-07] after it.
  • The tariff rule book is Latifa's: ten rules, each in English and Arabic.
  • No model was trained on it, and it changes every quarter.
  • Retrieve the rule, put it in the context, ask for an answer from it, with a citation.

The bad reply is the default behaviour of any generative model asked for a price it does not have: it completes a plausible sentence. Grounding does not make the model smarter; it changes the task from recalling to reading.

Two pipelines: one when the rules change, one for every question

Same two phases as yesterday's search, with a generator added at the end. Ten rules in two languages become 20 chunks. A chunk is one language of one rule: small enough to quote, large enough to answer. For long documents, chunking is a design decision to test; here the rules are short on purpose.

The generator's contract

Answer from the rules, cite the rule, or say the rules are silent

You answer customers of Sawaqi Water Company from the RULES given in the message and from nothing else. Answer in the language of the question, in one or two sentences, and cite the rule you used in square brackets, like [R-02]. If the RULES do not answer the question, reply exactly: NOT_IN_RULES
SourceFormCitationRefusal

The user message holds the three retrieved chunks, each starting with its rule id, then the question.

Each clause is checkable by code: a citation is a pattern, the refusal is an exact string. That is why the refusal is not a polite sentence: code must be able to count it and route the question to a person. A cited rule that was not among the retrieved ones is an invented citation: the lab's table shows the retrieved rules next to each reply so that this is visible.

The four silent questions are in the data on purpose: a farm discount, the price of a private tanker, paying cash at a petrol station, a solar heater refund. A retriever always returns its top three, so the generator receives rules that look related. Whether it refuses is the test. The key fact is checked as a string (a price, a number of days), which is crude and works for figures.

Reading a wrong answer

Locate the error before you change anything

The rule was not retrieved

Fix the retriever: wording, normalisation, a second search. The generator never had a chance.

Retrieved, answer wrong

Fix the prompt or the chunk: two tiers in one sentence, a figure copied from the wrong tier.

Silent question, answered

Read which retrieved rule it leaned on. Tighten the refusal clause; test it on more silent questions.

This is the same discipline as Day 1's "trace the failure to its cause", one level up. The lab prints the retrieved rules beside every reply for exactly this reading. Ask the room to classify three wrong answers from their own run before touching the prompt.

Checkpoint

The right rule, the wrong price

A customer asks what the second residential tier costs. The top chunk is R-02, which lists all four tiers. The reply says "SAR 1.20 [R-02]"; the rule says SAR 2.50. Where do you look first?

At the generator: the prompt and how the four tiers read in one sentence
At the retriever: return ten chunks instead of three
At the index: replace keywords by embeddings
At the model: fine-tune it on the rule book
Why. Retrieval did its job: the rule is in the context and is cited. The error is in reading it, so the fix is the prompt or the form of the chunk, for example one tier per line.

Answer: A. The first tier's price was copied instead of the second's: a reading error. A table-like chunk (one tier per line) and an instruction to quote the figure from the matching line usually fix it. Then add this question to the evaluation set.

Latency

Latency is a distribution: report the median and the 95th percentile

  • The median (p50) is what a typical message waits.
  • The 95th percentile (p95) is what one message in twenty waits. Budgets are written on it.
  • A hosted model's latency includes the network and a queue you do not control.
  • Sawaqi's budget: 300 ms at p95 per message.
4 · 5 ms
the baseline's p50 and p95 on a laptop processor (Lab 1.4)

A mean hides the queue

Nineteen fast calls and one of five seconds average to "fine".

The lab measures the wall-clock time of each call. On a free endpoint the p95 is often seconds, not milliseconds: that is a finding about the endpoint, and a paid or self-hosted endpoint of the same model will differ. Cached calls return at once, so the lab reports the latency recorded when the call was first made.

The prompted model as a classifier

Describe the eight departments, ask for one name, parse what comes back

SYSTEM = """You route one customer message of a water
utility to one department. ...
Departments:
- billing: a bill that is too high, a charge twice
- meters: a meter that is broken or reads wrong
...
Reply with the department name only."""

def parse_label(reply):
    low = reply.lower()
    found = [(low.index(d), d)
             for d in DEPARTMENTS if d in low]
    return min(found)[1] if found else None
  • No training data: the descriptions are the whole "training".
  • Parse leniently ("Department: leaks"), and count a reply with no department as wrong.
  • Temperature 0, a dozen output tokens.

This is the "prompted model as a zero-shot classifier" of the entry. Its strength is exactly where yesterday's baseline was weak: it needs no labelled Arabizi. Its weakness is the other three columns. The descriptions are worth iterating on: most routing errors of a prompted model come from two departments whose descriptions overlap.
