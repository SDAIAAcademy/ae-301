Fine-tuning an encoder

A pretrained encoder, a mean over real tokens, and eight scores

class Router(nn.Module):
    def __init__(self, encoder, n_labels):
        super().__init__()
        self.encoder = encoder
        self.drop = nn.Dropout(0.1)
        self.head = nn.Linear(encoder.cfg.d, n_labels)

    def forward(self, ids):
        mask = ids != 0              # padding out
        h = self.encoder(ids, mask)  # a vector per token
        pooled = (h * mask[..., None]).sum(1) \
                 / mask.sum(1, keepdim=True)
        return self.head(self.drop(pooled))
  • The encoder arrives pretrained: it has read Sawaqi-style messages without labels.
  • Pooling turns token vectors into one message vector. Padding is left out of the mean.
  • The head is new: 128 × 8 weights and 8 biases.
  • Full fine-tuning trains all 530,440 parameters.

The course encoder was pretrained by masked-token prediction on the text of the train and pool messages and on 10,000 further synthetic messages from other customers, none of them labelled and none from the validation or test splits: the script is _tools/pretrain_tiny.py in the labs folder. That stands for the unlabelled archive every organisation has. Many published encoders pool with a special first token instead of the mean; both work.

Sources: Devlin et al., BERT.

Lab 3.2, step 2

The training loop is the one you know, with two habits for small data

def train_epoch(model, opt, x, y):
    model.train()
    perm, total = torch.randperm(len(x)), 0.0
    for s in range(0, len(x), 32):
        idx = perm[s:s + 32]
        loss = F.cross_entropy(model(x[idx]), y[idx])
        opt.zero_grad()
        loss.backward()
        opt.step()
        total += loss.item() * len(idx)
    return total / len(x)

Mask 15% of the input tokens

Each epoch hides different tokens, as in pretraining. With 400 messages the model would otherwise learn single words by heart.

Keep the best validation epoch

Score the validation split after every epoch and keep those weights.

AdamW at a learning rate of 0.001 for this small model; a published base-size encoder wants about 0.00002. The token masking is a cheap augmentation: in the course's build experiments the encoder scored about 0.53 on the test split without it and about 0.63 with it. Say this openly, and say how such a choice should be made in their own work: on the validation split, with the test split measured once afterwards, as this session's checkpoints insist.

The idea

Freeze the weight matrix; learn its change as two thin matrices

Frozen W128 × 128 = 16,384 numbers
↓
A: 8 × 128 and B: 128 × 82,048 trainable numbers at rank 8
↓
OutputW x + (alpha / r) · B A x
  • The bet: the change a task needs is low rank, so two thin matrices can hold it.
  • B starts at zero: the adapted layer begins exactly as the pretrained one.
  • Rank sets capacity; alpha / r scales the update.
  • After training, add B A into W once: no extra latency when serving.

Low-rank adaptation was proposed by Hu and colleagues in 2021. Libraries such as PEFT apply it to published models in two lines; the lab writes the layer by hand in ten, so that the two-line version is understood. If both A and B started at zero, neither would receive a gradient.

Sources: Hu et al., LoRA: Low-Rank Adaptation of Large Language Models.

Lab 3.3, steps 1 and 2

The adapter layer is ten lines, and 1.7% of the model trains

class LoRALinear(nn.Module):
    def __init__(self, base, r=8, alpha=16):
        super().__init__()
        self.base, self.scale = base, alpha / r
        for p in self.base.parameters():
            p.requires_grad = False
        self.A = nn.Parameter(
            torch.randn(r, base.in_features) * 0.01)
        self.B = nn.Parameter(
            torch.zeros(base.out_features, r))

    def forward(self, x):
        return self.base(x) \
            + (x @ self.A.T @ self.B.T) * self.scale

Using adapters well

Adapters are for a skill on a large model, not for facts and not for small models

Good fit

A large model that does not fit your memory in full. Several tasks on one frozen model, one small adapter each.

Poor fit

A small model you can fine-tune in full. You pay quality and save nothing you need.

Wrong tool

Facts that change: prices, rules, dates. They belong in the rule book that Day 2 retrieves from.

The capstone's adaptation criterion asks for the comparison, not for the adapter to win. A defended "full fine-tuning, because memory was not our constraint" scores as well as a defended adapter.

Deploying

The decision is a function; the API is a thin layer over it

class Message(BaseModel):
    text: str = Field(max_length=2000)

class Decision(BaseModel):
    department: Optional[str]
    confidence: float
    variety: str
    handoff: bool
    reason: Optional[str]
    account_number: Optional[str]
    district: Optional[str]

@app.post("/route", response_model=Decision)
def route(message: Message) -> Decision:
    return Decision(**decide(message.text))
  • FastAPI with Pydantic: the schema validates what comes in and what goes out, and documents the service.
  • A message of 3,000 characters is refused with status 422 before the model runs.
  • A demo page at the root lets a colleague try a message without a tool. Gradio or Streamlit do the same with more polish.

The same Pydantic idea as Day 2's extraction schema, now as the contract of a service. The lab calls the app in the notebook's own process with a test client, so nothing has to listen on a port in class; capstone/service.py is the same code as a file to run with uvicorn. The account number and district come from exact patterns here: no hosted call in the request path, so no masking question and no network latency.

Sources: FastAPI documentation; Pydantic documentation, validators.
